# CAN velocity input for a bounded ROS execution diagnostic

This optional execution adapter supplies measured chassis forward/angular velocity to `/nso_csm/control_odom`. The default CLI still uses CSM-derived SE(2) velocity. Successful CAN mode preserves the measured CSM pose, scan stamp and raw twist on `/nso_csm/odom`, and its TF; only control vx/w change, with nonholonomic vy=0. No NSO score, candidate, circular planning model, return contract or ordinary reverse permission changes. The live DWA library was not patched.

The receiver has no transmit API. It selects the latest original kernel-timestamped CAN sample at or before the scan, with both scan-relative and current source/receipt ages at most150ms. It does not filter/interpolate, substitute zero, refresh old stamps or fall back to another velocity. The fixed150ms startup grace applies only before first successful pairing. CAN loss stops bridge publications and exits; the existing adapter observation TTL is up to500ms, so bridge exit must not be described as immediate chassis stopping. This source-loss chain has code/tests, not a new physical source-loss stopping trial.

A real receive-only check initially failed (60 scans,0 pairings). Its filter mask incorrectly included CAN_ERR_FLAG, directing the filter to the kernel error list. Simultaneous sockets received100 ordinary0x221 frames with the existing adapter mask and0 with the incorrect one. After matching the existing0xc00007ff mask,60/60 scans paired with300/300 admitted CAN frames, no drop and healthy source. ARM64 kernel timestamps were valid. The failure record is retained.

Twenty-six targeted tests passed, including default behavior, raw pose/TF preservation, freshness, future stamps, overflow, startup pairing and watchdog failure. A live checker initially compared entire ROS headers, including independent publisher sequence counters, and asserted; a subsequent20-message paired check confirmed equal pose, original stamp and frame. The bounded mission continued using its existing source/hardware protections; the checker failure was not a pose mismatch.

Two physical short offset-goal diagnostics with this explicit CAN profile are retained in `../forward_controller_20261107/probes/`:05 and06. They traveled0.178526m/8.214s and0.184944m/9.669s respectively; neither arrived, and both stopped after raw CSM pose jumps of57.54mm and50.11mm. CAN source pairing stayed valid and recorded control windows were not inverted. These are different actual starts, not matched efficacy runs or NSO actions. They establish that feedback adaptation was operating, not that navigation converged, semantic benefits exist or reconstruction is accurate. Camera extrinsics remain unverified after relocation.

Per-pair `/nso_csm/control_velocity_provenance` includes the original CSM/kernel stamps, both receipt/selection clocks, raw CAN frame, all source ages and raw/control twist. Only bounded diagnostic subscribers write it. The deployment and verification receipts identify the root-owned process and source hashes. Runtime files and tests are under `../../docs/research/onboard_20261104/deployment/hybrid/`.
